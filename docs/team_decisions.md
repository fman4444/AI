# 결정 기록 — 2G조

> 서기가 팀 PRD 인터뷰 중에 씁니다. 합의가 안 되면 오래 붙잡지 말고 **가정**으로 적고 다음 단계로 갑니다. PRD와 함께 커밋합니다.
> 구분: **결정**(합의함) · **가정**(일단 이렇게 두고 진행) · **질문**(만들기를 막는 것만 — 강사에게)

| 단계 | 구분 | 내용 | 다른 의견 (있으면) | 다시 볼 때 |
|---|---|---|---|---|
| 1 왜 | 결정 | 해결할 불편 = 근태를 제각각 받아 모으고, 평가기준에 대조해 계산하고, 기준이 바뀔 때마다 다시 따지는 일 | | |
| 2 누가 | 결정 | 주 사용자 = 부서원(약 50명)과 검토 담당자, 같은 비중. 부서원이 목요일 퇴근 전까지 금요일 근태를 입력하고, 금요일 근태로 실적 달성 여부를 체크한다 | | |
| 2 누가 | 가정 | 검토 담당자 수는 정하지 않음 — 이번 시연은 검토 담당자 한 사람 기준 | | 리뷰 때 |
| 3 무엇을 | 결정 | 핵심 기능 3개(우선순위 순): ① 개인 근태 입력(기능 A `IN`) ② 충족 여부 검토(기능 B `board`) ③ 미입력자 현황. 다음 단계: 평가기준 설정, 검수·확정, 메인 요약 강화, 50명 실제 수합 | | |
| 3 무엇을 | 결정 | 평가기준: 부서원 전체인원 중 평가대상자의 50% 이상이 개별 실적을 달성해야 한다. 개별 실적 달성 = 금요일 8시간 근무 중 4시간 이상 부재(휴가, 출장). 평가대상자 = 전체인원 − 교육대상자 | | |
| 3 무엇을 | 가정 | 근태 항목을 '근무 유형'에서 '부재 유형(없음·휴가·출장) + 부재 시간(0~8)'으로 바꿨다. 반차는 휴가 4시간으로 입력한다 | | ② 기능 A 착수 전 |
| 3 무엇을 | 가정 | 미입력자 현황은 `board` 페이지에 둔다(③ 담당) | | 리뷰 때 |
| 3 무엇을 | 가정 | 근태를 입력하지 않은 평가대상자는 분모에 넣고 달성으로 세지 않는다 | | ④ 기대값 작성 전 |
| 3 무엇을 | 가정 | 같은 사번·같은 날짜 근태가 두 건 이상이면 "확인 필요 — 중복 입력"으로 따로 보이고, 달성 판정과 미입력자 목록에서 뺀다(분모에는 남김). 이것이 표본의 일부러 넣은 함정이다 | | ④ 기대값 작성 전 |
| 3 무엇을 | 가정 | `IN`에서 같은 사번·같은 날짜를 다시 저장하면 기존 건을 고친다 | | ② 기능 A 착수 전 |
| 4 어떻게 | 결정 | 여러 페이지 HTML 웹앱, GitHub Pages 배포, 서버·로그인·외부 전송 없음. 이번에는 검토 담당자 한 사람이 가상 표본으로 입력부터 검토까지 시연한다. 50명 실제 수합은 다음 단계 | | |
| 4 어떻게 | 결정 | 기능 A 영문 = `IN`, 기능 B 영문 = `board`, 조 이름·조직 영문명·팀 레포 이름 = `team2g` | | |
| 4 어떻게 | 가정 | localStorage 키 = `team2g_app`. 기능 A 파일은 대문자 그대로 `tools/pages/IN.html`, `tools/assets/IN.js` | | 뼈대 PR 때 |
| 4 어떻게 | 결정 | 배포 주소는 실제 저장소 기준 `https://lh-axcamp.github.io/W02C03-team2G/tools/index.html`로 한다(처음 알려 준 team2g.github.io/team2g 대신) | | |
| 4 어떻게 | 가정 | 표본은 `data/team_sample.json` 하나(저장 JSON과 같은 모양)이고 시작 페이지 '가져오기'로 불러온다 | | ④ 표본 작성 때 |
| 4 어떻게 | 가정 | 제작 시간은 실습 당일 시간 안 | | |
| 5 성공 | 결정 | 핵심 지표 2개, 같은 비중: 부서별 충족 여부 판정 · 미입력자 목록. 판정은 "담당 검토 후 확정" — 검증 담당 확인 ☐ | | |
| 5 성공 | 가정 | 성공 시나리오 S1~S4(`prd/team_prd.md` 5절)는 세션이 평가기준에 맞춰 제안했다 | | ④ 수용 기준표 작성 때 |
| 4 어떻게 | 결정 | 조원은 3명이고 메인 PC 한 대에서 함께 진행한다. 역할(①~④)을 사람별로 나누지 않고, 파일 담당과 커밋 머리를 정하는 데만 쓴다. 승인·병합은 PR을 만든 조원과 다른 조원 계정으로 한다(시크릿 창) | | |
| 4 어떻게 | 결정 | GitHub 작업 이슈는 만들지 않는다. PR 본문 첫 줄은 "{역할} {작업 이름} — 작업 이슈 생략(조 결정)"으로 쓴다 | | |
| 4 어떻게 | 결정 | 조원 합의로 PR 승인 단계를 생략한다. PR 만들기와 병합은 드라이버 PC의 Claude 세션이 진행한다(팀 규칙의 리뷰 짝 승인·사람 병합 대신) | | |
| 5 성공 | 결정 | 조원 요청으로 수용 기준표 기대 결과(2·3절)를 Claude 세션이 표본 파일을 직접 세어 적었다. 웹앱을 돌리기 전에 적었고 웹앱 결과를 옮기지 않았다 | | 1차 시험 때 |
| 4 어떻게 | 결정 | 배포(GitHub Pages)는 생략하고 HTML 만들기에 집중한다. 배포 주소가 404였고 Pages 설정은 사람이 레포 Settings에서 켜야 한다. 시험과 확인은 main 파일(`tools/index.html`)로 한다 | | Pages를 켤 수 있게 되면 |
| 4 어떻게 | 결정 | 조원 3명이 역할(①~④)을 나누지 않고 드라이버 PC 한 대의 세션 하나로 산출물 한 벌을 만든다. CLAUDE.md의 "역할별 담당 파일만 수정"과 "리뷰 짝" 규칙은 적용하지 않고, 문서의 역할·이름 칸은 "조 전체(드라이버 세션)"로 적는다 | | |
| 4 어떻게 | 결정 | 사람이 하는 화면 확인·조원 리뷰·다른 조 교차 검증은 생략하고 Claude 세션의 AI 자동 시험(Playwright, file://)으로 대신한다. 결과에는 "AI 자동 시험 — 사람 확인 아님"을 표기한다 | | |
| 4 어떻게 | 결정 | 배포 주소 칸은 "배포 안 함 — ZIP을 풀어 tools/index.html을 엶"으로 적는다 | | |
| 기타 | 결정 | 원격 브랜치 `claude/zealous-babbage-azgwrr`(주제 "공공임대 하자 접수 점검" 프로젝트 카드)는 우리 작업과 상관없는 주제라 합치지 않는다 | | |
| 4 어떻게 | 결정 | 드라이버 계정 병합(조 결정) — 팀 PRD ④부터도 PR 만들기와 병합은 드라이버 PC의 Claude 세션이 바로 한다 | | |
| 6 제출 | 가정 | 시연 대본 "마감 전 확인" 네 줄은 조원이 "추천대로"라고 답해 체크했다. 첫 줄(열린 PR 없음)은 팀 PRD ⑥ PR 병합 뒤 GitHub에서 열린 PR 0개를 확인하는 조건이다 | | 병합 직후 |
| 보강 디자인 | 결정 | 레퍼런스 = LH 홈페이지(lh.or.kr). 세션은 네트워크 정책으로 열지 못해 조원이 올린 캡처 2장으로 봤다. 가져올 것: 바로가기 카드, 공지 목록의 탭·꼬리표, 두 가지 색 굵은 제목 | | |
